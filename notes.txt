### Architecture decisions: survey the fleet first
An architecture decision is anything involving security/authentication, config structure, HTTP clients, error handling, logging, dependencies, package structure, testing approach, or deployment config. For any of these:
1. Survey at least 10 services in the project root.
2. Trace each one's implementation fully (see Deep tracing).

### Deep tracing: don't stop at a service's own source
Behavior often comes from outside a service's src folder. Before concluding "this service doesn't do X", check:
- Build files: pom.xml, the parent POM/BOM, and the full dependency tree (`mvn dependency:tree`). Identify internal/company libraries.
- Internal libraries: inspect what they actually do. Find the jar in the local Maven repository, unpack it, and read the sources jar or decompile the classes.
- Spring auto-configuration inside dependency jars: META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports, spring.factories, @Conditional* annotations, @Enable* annotations, @Import, and component scanning of library packages.
- Filters, interceptors, security config, and aspects.
- application.yml and profiles, plus the FCM config repo for each environment.
- OpenShift/deployment config if present in the repo.
If a behavior exists in other services but you can't find where it's implemented, say so and keep tracing. Never conclude it isn't there.
