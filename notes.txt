I thought this issue was fixed. The service layer now commits the flag to the DB
immediately when it returns. But I have observed something else.

BACKGROUND

We submit an async task to the chargeback domain service. That service can update
this flag to N, Y or F -- it can change it to anything except P.

So the race is: our service layer sets the flag to P, the async chargeback domain
work then sets it to something else, and the recon batch overwrites it afterwards.

HOW I REPRODUCE IT

In my test environment every record in the DB is already P. The batch only picks up
records with N or F, so nothing gets picked up. To test, I manually update one
record's flag to N so the next cron run picks it up.

WHAT I OBSERVE, STEP BY STEP

1. AccountStagingReader line 75 is triggered, then 76, 77, and on from there.
2. At line 84 it submits to the executor class.
3. The executor calls the recon service to update the flag immediately.
4. When that returns, line 115 updates the flag to P. This part is expected.
5. Execution moves from 115 to 120, exits processThrottleStagingInfo, and returns
   to the reader.
6. Back in the reader, debugging continues for a while, and then right at the end --
   as it exits the read method in AccountStagingReader -- the flag is updated to P
   again.

THE PROBLEM

The flag is written to P twice: once in the executor at line 115, and again on the
way out of AccountStagingReader.read(). If the async chargeback domain service set
the flag to N, Y or F in between those two writes, that second write silently
overwrites it and the record goes back to P.

WHAT I NEED

Find where that second update to P at the end of the read method is coming from,
and tell me how to stop the reader from re-writing the flag after the executor has
already committed it.
